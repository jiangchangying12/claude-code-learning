理解 Claude Code 的運作原理

作者：西見公宏。到目前為止，我們學了 Claude Code 的基本用法與實務活用。光憑這些就足以使用，但若要讓它更照你的意圖運作，關鍵在於——把 Claude Code 理解成一個「AI 代理」。本章拆解它內部的運作原理，讓你日後遇到問題時，能準確判斷「是哪個環節出了狀況、該用哪個功能解決」。

🎯 本章兩大主軸 ① 把 Claude Code 理解為由「環境・知覺・記憶・推論・行動」五要素構成的 AI 代理。
② 認識實務活用時的三大課題，並理解它們各自對應哪個要素（這是第 7 章解法的鋪陳）。

6.1　把 Claude Code 理解為 AI 代理

回顧第 4 章，我們靠整備 CLAUDE.md 與文件群，讓 Claude Code 做出一致的開發。當時它的典型動作是這樣的：

使用者：「請新增優先度篩選功能。」
Claude Code 依序：① 讀 CLAUDE.md 確認專案規則 → ② 讀 product-requirements.md 理解需求 → ③ 讀 architecture.md 掌握實作方針 → ④ 搜尋既有元件確認樣式 → ⑤ 在 .steering/ 建計畫文件 → ⑥ 開始實作 → ⑦ 執行測試 → ⑧ 出錯則修正 → ⑨ 重新測試 → ⑩ 更新文件。
圖 6.1　第 4 章中典型的 Claude Code 動作

它能這樣自主運作，是因為它被實作為一個 AI 代理。

AI 代理的機制：五個要素

如第 1 章所述，AI 代理是「針對指定目標、自主行動以達成」的系統，目標是完成人類的知識型任務。它由五個要素構成，協同運作：

圖 6.2　AI 代理的動作流程

① 環境：AI 代理作用的場所

環境是代理「取得資訊、並透過行動施加變化」的對象。不同種類的代理，環境也不同：

種類環境知覺行動
自動駕駛車道路、號誌、行人攝影機、雷達、GPS方向盤、油門、煞車
工廠機器人生產線、零件攝影機、位置感測器手臂移動、夾取、組裝
Web 導覽代理網頁、表單、連結HTML 結構、文字點擊、輸入、捲動
程式設計代理原始碼、設定檔、文件檔案內容、指令結果編輯檔案、執行指令
表 6.1　不同種類 AI 代理的對象環境差異

對 Claude Code 而言，環境＝參照專案程式碼庫的檔案系統＋程式碼的執行環境。它透過檔案系統讀專案的程式碼（如 src/components/TaskList.tsx、docs/architecture.md），並執行 npm、git 等指令與執行環境溝通（命令列、經指令存取資料庫/外部 API）。

情境1 建立檔案：行動 Write('src/Profile.tsx', code) → 環境：建立新檔 → 知覺：確認 Profile.tsx 已建立。
情境2 執行測試：行動 Bash('npm test') → 環境：執行測試 → 知覺：成功「✓ All 15 tests passed」／失敗「✗ 2 tests failed…」。
情境3 編輯程式碼：行動 Edit('src/api.ts', 25, newCode) → 環境：第 25 行被改 → 知覺：確認變更已套用。
圖 6.3 / 6.4　Claude Code 對象的環境與互動（「行動→環境反應→知覺」是基本動作模式）

② 知覺：從環境接收資訊

知覺＝從環境或使用者取得資訊的過程，相當於人類的五感。Claude Code 的知覺主要以「工具的執行結果」取得：

・檔案系統：Read('src/App.tsx') → 知覺到該檔內容。
・命令列：Bash('npm test') → 知覺到 PASS/FAIL 與錯誤詳情。
・Web API：WebSearch('React 19 新功能') → 知覺到搜尋結果。
・使用者輸入：知覺到「請新增個人檔案編輯功能，並依既有樣式實作」這類指示。
圖 6.5　知覺的種類與具體例
⚠️ 為什麼知覺很關鍵知覺得到的資訊會在下一步推論被分析、成為行動依據。若知覺不正確，推論與行動也會跟著出錯。

③ 記憶：保留過去的經驗與知識

沒有記憶，代理每次都得從零重想。記憶依保留期間分兩類：

類型是什麼特性
短期記憶情境視窗（context window）容量有限；長對話會導致「忘記」過去指示
長期記憶外部檔案 / 資料庫容量實質無限；需要時才載入短期記憶
圖 6.6　記憶的分類

Claude Code 的短期記憶＝情境視窗，指「LLM 生成新文字時可參照的文字總量 ＋ 所生成的全部新文字」。載入 CLAUDE.md、Read 檔案、WebFetch、保留 Bash 結果……至今所有動作都會消耗它。

🧠 帶出「情境工程」使用者「它記得我之前說的話」這種體驗，取決於「能多好地管理情境視窗內的記憶」。這種管理就叫情境工程（Context Engineering）——正是第 7 章的主題。

④ 推論：決定下一步行動

推論＝依「知覺到的資訊 ＋ 記憶」判斷下一步該做什麼，是代理的「思考」、智能核心。由 LLM（Claude）執行：

LLM 推論的輸入（提示）：系統提示 ＋ 使用者指示「新增個人檔案編輯功能」＋ CLAUDE.md（「務必確認 README.md 與 architecture.md」）＋ 會話歷史 ＋ 工具執行歷史。
輸出：選擇工具 Read、參數 { path: "README.md" }，推論結果「為理解整個專案，先讀 README.md」。
圖 6.7　LLM 的推論

LLM 綜合提示中所有資訊，決定下一個工具與參數。推論品質決定代理的智能。 Claude Code 可選 Opus／Sonnet／Haiku：複雜、需長步驟的任務用 Opus，其餘用 Sonnet 或 Haiku。

🧪 MEMO：想推論更深就用 ultrathink Claude Code 內建「擴展思考模式」，在提示放入關鍵字即可啟用，提高思考預算（內部約略消耗的 token）：
關鍵字思考預算（約）說明
think約 4,000 token輕度推論
think hard / megathink約 10,000 token更深入的分析
think harder / ultrathink約 31,999 token非常詳盡，最適合長時間/複雜任務
表 6.2　指示關鍵字對應的思考預算

檔案操作Read、Write、Edit、MultiEdit

Web 存取WebSearch、WebFetch

6.2　活用程式設計代理時的三大課題

五要素協同讓 Claude Code 自主執行複雜任務。但實際活用時會碰到「動作與意圖不同」的課題，而它們與五要素密切相關：

課題對應要素原因
1. 忘記過去的指示記憶情境視窗容量限制
2. 不照意圖運作推論隱性期待未明示、資料間衝突
3. 無法妥善連動外部系統行動預設工具種類不足、MCP 未必選對
表 6.4　課題與 AI 代理要素的對應關係

課題 1：忘記過去的指示

一開始 Claude Code 能正確理解 architecture.md、做出一致判斷；但任務一長、工具執行一多，就會發生：

開始（步驟 1–20）：「依 architecture.md，按 UI 層→服務層→資料層實作。」
中盤（步驟 50–70）：「正在實作個人檔案編輯，接著寫測試。」→ 還記得設計判斷。
後半（步驟 100+）：「我來修錯。建立直接存取資料層的元件。」→ 用了 architecture.md 禁止的樣式！
使用者：那是被禁止的樣式。Claude Code：抱歉，我確認 architecture.md……→ 明明一開始讀過卻忘了。
圖 6.10　長時間任務中設計判斷的喪失

這不是單純的故障，而是源於記憶機制的結構性問題。長任務中三項因素連鎖作用：

(1) 每次工具執行都消耗記憶。Claude Code 是「不斷選工具的代理」，任務越進行、情境越龐大：

步驟操作讀入 token累計
1Read('CLAUDE.md')約 1,0001,000
3Read('architecture.md') ← 重要規則約 1,5004,500
50Bash('npm test') ← 大量日誌約 15,000約 50,000
100（累計）—約 120,000
圖 6.11　工具執行造成的情境消耗（步驟 3 讀的 architecture.md 細節，後期很可能已被壓縮或丟棄）

尤其 Bash 跑測試/建置會輸出大量日誌（含堆疊追蹤），一次就吃掉數千～數萬 token。

(2) 情境視窗的自動壓縮（auto-compaction）。當情境達門檻（預設約 95%），Claude Code 自動執行壓縮，把會話與工具歷史摘要化：

壓縮前：系統提示＋CLAUDE.md＋全部會話歷史＋全部工具執行歷史（含 architecture.md 的 1,500 token 細節、npm test 的 15,000 token 日誌、100+ 次執行紀錄）。
壓縮後：系統提示（保留）＋CLAUDE.md（保留）＋壓縮摘要（「正在實作個人檔案編輯，UI 與服務層完成，現進行資料層整合與測試」）＋最近 5 個檔案內容。
可能流失：❌ architecture.md 的詳細規則 ❌ 初期設計判斷的理由 ❌ 中間步驟的試錯歷史。
圖 6.12 / 6.13 / 6.14　自動壓縮的執行與推測機制

(3) Context Rot（情境腐化）。更根本的問題：情境越大，LLM 效能本身越下降——隨輸入 token 增加，正確參照/理解的能力下降。

🔬 Chroma 公司的實驗（2025/7） 以 18 種 LLM（GPT-4.1、Claude 4、Gemini 2.5、Qwen3…）測試，刻意固定任務難度、只改輸入長度。即使是「原封不動複製 apple apple…」這種人類複製貼上絕不會錯的極簡任務，輸入一長，所有模型分數都下降：
輸入長度分數表現
50–100 字幾乎所有模型 0.95–1.0（部分已驟降到 0.7–0.8）
1,000 字Claude 系列（除 Haiku）維持 0.9+，多數模型降到 0.6–0.7
2,500–5,000 字僅 Claude Opus 4 維持 0.9 附近，多數降到 0.5–0.6
10,000 字以上幾乎都貼在 0.5、無法完成；僅 Opus 4 守在 0.7 附近
圖 6.15 / 表 6.5　Repeated Words 任務：輸入越長、分數越低
📌 啟示Sonnet 4/4.5 雖有最大 100 萬 token 上限，但實際能發揮效能的輸入，遠比上限短。重點不是塞大量資訊，而是「用更少 token 高效傳遞」。

課題 2：不照意圖運作

這與課題 1 的「遺忘」不同——它讀過規則、也理解，實作時卻選了別的做法：

使用者：請依 architecture.md，遵守「UI 層必經服務層存取資料」。
Claude Code 實作出：const userData = await db.users.findOne({id}) ← 直接存取資料層（被禁止的樣式）！
圖 6.16　不遵守架構規則

(1) 隱性期待未明示。專家心中「理所當然的步驟」沒寫進文件：

專家實際流程：讀 README → 讀 architecture.md → 用 Grep 搜尋既有類似功能 → 讀既有實作 → 確認既有樣式（服務層呼叫、錯誤處理） → 同樣式實作 → 測試…
但 CLAUDE.md 只寫：「實作新功能時務必確認 README.md 與 architecture.md」→ 中間「搜尋與確認既有樣式」三步沒寫。
結果：對 Claude Code 而言，沒寫的步驟＝「選用」而非「必須」→ 跳過 → 做出與既有樣式不一致的實作。
圖 6.17 / 6.18　未明示的隱性期待，導致步驟被省略

(2) 資料間衝突。多份文件指示矛盾時，代理無法判斷該優先誰：

architecture.md：「UI 層務必經服務層，禁止直接存取資料層。」
development-guidelines.md：「效能重要的畫面，建議直接存取資料來源。」
既有 Dashboard.tsx：為效能直接存取。
→ 收到「擴充儀表板」時，三者矛盾、又沒明示優先順序 → 第 1 次照 architecture.md（與既有不一致）→ 被要求照既有 → 第 2 次直接存取（違反 architecture.md）→ 來回打轉。
圖 6.19 / 6.20　資料間矛盾的指示造成的混亂
💡 常見成因「總之塞大量資料、讓 Claude 自己判斷」這種無計畫地餵資料，最容易引發這種衝突。

課題 3：無法妥善連動外部系統

團隊開發要與各種外部系統連動（GitHub Issue/PR、Figma、瀏覽器驗證…）。第 3 章的 MCP 能用標準化方式連動，但即使註冊了 MCP，代理也未必在期待的場景啟動期待的工具——它依各工具的名稱與描述、連同預設工具一起選，因此「是否選對」受 MCP 工具描述是否具體影響。結果可能選不到適當 MCP，反而自己從零生成程式碼。

🛠️ 補充手段別過度依賴 MCP，讓 Claude Code 用 Bash 操作 CLI 工具也很有效（性能強、更彈性）。但 Bash 幾乎能做本機任何事，因此需同時把執行環境沙箱化（第 7 章詳解）。

6.3　本章小結

✅ 一句話總結Claude Code ＝由「環境・知覺・記憶・推論・行動」五要素構成、不斷依知覺選擇工具的 AI 代理。

三大課題與根因：

  • 忘記過去指示：情境視窗容量限制 ＋ Context Rot 造成效能下降。
  • 不照意圖運作：隱性期待沒寫出來、或多份資料指示衝突，導致代理混亂。
  • 無法妥善連動外部：即使用 MCP，也無法保證選到期待的工具。

第 7 章將給出對應解法：情境工程（壓縮／結構化筆記／子代理）、提升指示追從性（斜線指令／技能／鉤子）、外部連動與安全（MCP／Bash／Sandboxing）。
