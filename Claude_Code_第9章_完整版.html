第 9 章 · 機制化【實踐篇】

把規格驅動開發的流程機制化（實踐篇）

作者：西見公宏。第 8 章建好機制，本章用無頭模式（headless）把它自動跑起來，體驗「互動執行＋自動執行」結合的開發流程，並學會用 LLM 分析執行日誌、持續改善機制。

🎯 本章重點無頭模式＝不對話、以程式方式執行 Claude Code，搭配斜線指令/技能/子代理即可自動化整個開發流程。

9.1　以無頭模式完全自動化

之前都是互動執行（REPL）；雖能自動化複雜流程，但某些步驟仍要使用者核准。無頭模式則「事先以指令指定動作、從頭到尾自動」。

基本用法與差異

互動模式可按 shift+tab 切換三種權限模式（一般→自動編輯→計畫）；無頭模式則用 -p/--print，一次指示、無對話完成：

claude -p "請說明 src/ 的程式碼"           # 命令列引數
echo "請說明 src/ 的程式碼" | claude -p     # 標準輸入
cat prompt.md | claude -p                  # 從檔案
選項說明
--print, -p無頭模式執行
--output-formattext / json / stream-json
--model指定模型
--dangerously-skip-permissions跳過所有權限確認
--allowedTools / --disallowedTools限制可/不可用的工具
表 9.1　無頭模式常用選項
⚠️ 安全--dangerously-skip-permissions 在未隔離環境很危險；若不在 Docker 隔離，建議用 --allowedTools/--disallowedTools 限制——因為難以預測它會執行什麼指令，最壞可能破壞環境。

格式用途

stream-json（需 --verbose）逐則 JSON 即時串流，便於追蹤進度與事後分析軌跡

自動開發 MVP 的指令

prompt.md 只放一行 /add-feature 請開發產品需求定義書中的核心機能（MVP）。（因 /add-feature 已含全工程，呼叫即完結）。指令範例：

cat prompt.md | claude -p --dangerously-skip-permissions \
  --output-format stream-json --verbose \
  --model claude-sonnet-4-20250514 2>&1 | tee output.jsonl

各部分：cat … | 把提示從標準輸入餵入；-p 無頭；stream-json --verbose 即時記錄；--model 指定模型；2>&1 | tee output.jsonl 把含錯誤的全部輸出邊顯示邊存成 JSON Lines。

🤔 為何選 Sonnet 4 而非 4.5？ 無頭模式不指定時預設 Sonnet 4.5，但 4.5 在互動下品質高、卻常停下發問（「這實作可以嗎？」），無頭下人無法回應就會中斷。實測 Sonnet 4 較少中途徵詢、較能一路跑到底，故本章刻意選它。建議：常用無頭就建「基準測試」機制，每次模型更新都比較動作差異。

9.2　【實踐】任務管理 App 的自動開發

和第 4 章同一個 App，這次全自動。流程：

① 準備構想筆記（docs/ideas/initial-requirements.md，寫好概念/主要機能/非機能需求）
② REPL 互動跑 /setup-project 生成 6 份文件、逐份核准 → 跑 /review-docs 審查並反映指摘
③ 無頭模式跑 /add-feature（上面的指令）→ 自動產出可用的 task CLI（含 add/list/show/start/done/delete，Git 整合）
④ 計畫紀錄留在 .steering/YYYYMMDD-[機能名]/tasklist.md
圖 9.9–9.19　從文件到自動實作出 task CLI
⚠️ 務必 Dev Container因 --dangerously-skip-permissions 放行所有工具，務必在 Dev Container 執行。即便如此，仍可能透過 WebFetch 把容器內可存取的認證資訊帶到外部，動手實作時要留意。

分析無頭執行的日誌

用 steering 技能要求「作業中務必更新 tasklist.md」，但模型/Claude Code 更新後可能失靈。此時保存的 output.jsonl 就派上用場——但日誌常達數百 KB、難目視。

🔎 用 LLM 分析日誌 筆者群用 Google Gemini 2.5 Pro / Google AI Studio 分析較具參考性。把 .jsonl 改副檔名為 .json 上傳，提示：「這是 Claude Code 執行日誌，請依時序整理代理行動、並提具體改善建議」。它會把行動拆成「準備計畫→實作→品質檢查與自我修復→E2E 測試與完成」四階段，並建議導入 TDD、縮短回饋循環（近似 CI）、強化專案特有規則學習等。注意：未啟用付費帳單時，Google AI Studio 屬「免費服務」、送出資料可能被用於訓練；機密資料請用付費服務。
💡 核心方法無頭模式難即時看「斜線指令是否執行、技能是否載入、是否照 tasklist 走」，用 LLM 分析日誌找原因，再修正技能/提示、轉動實驗循環。

9.3　如何更進一步發展

三者分工再強調：技能定義「做法」、斜線指令定義「流程」、子代理做「獨立驗證/分析」。擴充方向：

  • 技能依三單位擴充：成果物（API 規格書、測試計畫書…）／任務（效能測試、DB 遷移、資安掃描…）／領域（法規要件、品牌指南、商業規則）。
  • 斜線指令：把新定型作業指令化（修 bug、重構、效能改善流程）；既有指令派生專門版（如 /add-feature-with-migration 加入遷移檔審查步驟）；調整核准點（重品質就每份都核准、重速度就事後審查）。
  • 子代理：特化於大量讀檔（影響範圍分析、資安調查）與專門驗證（資安審查、無障礙檢查）；回傳結構化報告，必要時把報告存檔供日後參照。

9.4　本章小結

🧭 最終心法 工具與代理本身更新太快、無法全部跟上。把 Claude Code 理解為 AI 代理、學會切分問題、依意圖活用功能，才是能遷移到任何代理的核心能力。第 8、9 章只是把第 4 章流程「單純機制化」，請以此為起點，打造符合自身團隊/專案的獨有機制。
