第 7 章 · 解決三大課題

讓 Claude Code 照意圖運作

作者：西見公宏。第 6 章認識了三大課題（忘記指示、不照意圖、外部連動），本章給出對應解法：① 以情境工程管理記憶 ② 以斜線指令／技能／鉤子提升指示追從性 ③ 以 MCP／Bash＋Sandboxing 實現安全的外部連動。

🗺️ 課題 → 解法對照 忘記指示（記憶）→ 情境工程；不照意圖（推論）→ 斜線指令/技能/鉤子；外部連動（行動）→ MCP/Bash/沙箱。

7.1　情境工程（Context Engineering）

情境工程＝管理 AI 代理「有限的情境視窗（記憶容量）」的技術。就像人類靠「做筆記、整理、把重要東西放在好拿的地方」管理記憶，代理也需要。Anthropic 工程團隊提出三策略：

策略做法時機效果
① 壓縮 Compaction把舊記憶摘要、以新情境延續情境超過門檻時保連續性、騰出容量
② 結構化筆記把重要資訊寫到外部檔案持久化從任務開始就持續不受壓縮影響、進度可視
③ 子代理架構用獨立情境執行專門任務產生大量日誌時不污染主情境
圖 7.1　情境工程的三項策略（可單用，複雜任務組合更有效）

策略 1：壓縮（Compaction）

情境達門檻（預設約 95%）時自動執行：把會話與工具歷史摘要成一段，再以「系統提示＋CLAUDE.md＋摘要＋最近 5 個檔案」繼續（圖 7.2）。但壓縮可能流失 architecture.md 細節、設計理由、試錯歷史（圖 7.3）。三種因應做法：

  • (1) 清除工具結果：刪掉大量日誌、保留「執行過測試」的事實（圖 7.4）。對輸出大量日誌的 Bash 測試/建置特別有效。可讓指令把細節寫日誌檔、標準輸出只給概要；或用「回傳去蕪存菁結果」的 MCP/CLI 取代會抓一堆 HTML 的 WebFetch。
  • (2) 依里程碑手動 /clear（圖 7.5）。好時機：階段完成後、功能完成後、發生大量錯誤日誌後。壞時機：實作途中、複雜設計判斷剛做完。
  • (3) 壓縮前外部化：把重要資訊先寫到外部檔——即下面的「結構化筆記」。

策略 2：結構化筆記（Structured Note-Taking）

把重要資訊以「情境視窗外部的檔案」持久化，就不受壓縮影響。第 4 章的 .steering/ 目錄就是實例（requirements/design/tasklist，可再加 blockers.md、decisions.md）。

🎮 例：Claude Plays Pokémon 把 Claude 接到《寶可夢 紅》，沒人教它「記憶結構怎麼建」，它卻自行把地圖、目標、策略、成就結構化記錄；情境重設後讀回筆記，仍能延續數小時的練功與探索。第 4 章的 .steering/ 就是把同樣思維以 CLAUDE.md 明確規定下來，確保資訊被記錄。

三個要點：① 從任務開始就建筆記 ② 定期更新（如「各階段完成自動更新 tasklist.md」）③ 重要決定必記理由（decisions.md）。

策略 3：子代理（Sub-agent）架構

子代理＝擁有「獨立於親代理情境視窗」的專門化 AI 助理。親代理用 Task 工具委派，只收回簡潔報告。關鍵：情境分離——子代理讀大量日誌也不影響親代理（圖 7.9）。

場景1：自動測試輸出數萬行日誌 → 讓 test-runner 子代理執行，日誌只留在它的情境，親代理只收簡潔報告。
場景2：調查資安漏洞要讀數百檔 → 讓 impact-analyzer 讀完分析，只回傳「有影響的 23 個檔案清單」。
圖 7.10　子代理發揮效果的場景

子代理以 Markdown 定義（frontmatter＋系統提示）：

---
name: test-runner
description: 執行測試與分析失敗的專門代理。測試後自動使用。
tools: Read, Bash, Grep, Glob
model: sonnet
---
你是測試執行與錯誤分析的專家。被呼叫時：1.執行測試 2.找出失敗 3.分析錯誤 4.找出原因。
務必產出簡潔報告，讓親代理能立刻行動。
frontmatter必須說明
name✓唯一識別子（小寫＋連字號）
description✓用途；Claude 用來判斷何時啟動
tools選用允許工具；省略則繼承親代理全部
model選用sonnet/opus/haiku/inherit

⚠️ 子代理的限制與正確用法 子代理無法存取親代理情境，所以不適合「依先前溝通做具體實作」（易偏離意圖）。依筆者經驗，適合把會壓迫情境的任務交給它：審查（code-reviewer）、資訊蒐集（impact-analyzer）、大量資料處理（test-runner）。用「報告驅動」：做完回傳簡潔報告，代理間靠檔案（Markdown/Issue）共享資訊。

內建的 Plan 子代理：計畫模式下自動啟動，用獨立情境探索程式碼庫、回傳調查結果讓親代理擬計畫——避免大量讀檔壓迫主情境，也防止誤啟動其他子代理。子代理放 .claude/agents/（專案）或 ~/.claude/agents/（全域），用 /agents 管理。

7.2　提升指示追從性

三個工具解決「不照意圖運作」：

工具解決機制確實性呼叫
斜線指令明示隱性步驟Markdown 定義工作流程依賴提示使用者/工具執行
技能 Skill改善工具使用判斷教用法並遵守依賴提示Claude 自動判斷
鉤子 Hook強制遵守事項以程式實作規則必定遵守觸發條件啟動
表 7.3　三種功能的比較

斜線指令：明示「工作流程」

把常用提示存成 Markdown、一鍵呼叫，最適合把「做什麼、什麼順序」的工作流程白紙黑字寫下，一次定義、團隊共用、防屬人化。例：

---
description: 依既有樣式實作新功能
---
# 新增功能
## 1. 理解專案：讀 README.md、確認 architecture.md
## 2. 調查既有樣式：用 Grep 搜尋類似功能、讀實作、確認服務層呼叫/錯誤處理/測試寫法
## 3. 實作：依既有樣式，遵守 architecture.md 分層
## 4. 測試與驗證：出錯則重看 architecture.md、修正重測
## 5. 更新文件

呼叫：/add-feature 使用者個人檔案編輯。進階：用 $ARGUMENTS 帶參數、@檔名 參照檔案、!`指令` 把 Bash 結果納入情境；frontmatter 可設 allowed-tools 限制工具（表 7.4）。原則：單一職責、適當粒度（一次作業階段能完成）、明確執行流程。

技能 Skill：教「工具用法與思維」

斜線指令明示「做什麼/什麼順序」；技能教「怎麼用工具、思維本身」，且不需明確呼叫，Claude 自動判斷相關性後載入，整個工作階段有效。結構是「SKILL.md ＋ 輔助檔（腳本/範本/文件）」的目錄。

📚 技能 vs CLAUDE.md（漸進式揭露） CLAUDE.md 永遠全文載入（無關作業也吃情境）；技能採漸進式揭露：① 先載 name/description（約 100 token）判斷相關 → ② 才載 SKILL.md 本文（<5,000 token）→ ③ 按需載輔助檔。所以 CLAUDE.md 放「整體方針」，技能放「TypeScript 怎麼寫、資安怎麼審」這類局部知識。

它解決：① 大型規約壓迫情境（把各領域規則拆成 typescript-standards、react-standards… 各自的 SKILL.md，做前端只載前端相關）② 多模式切換（frontend-patterns / backend-patterns / legacy-maintenance，在 description 寫觸發場景，自動選用）。SKILL.md 例：

---
name: typescript-standards
description: TypeScript 開發的規約與最佳實務。撰寫 TS、定義型別時使用。
allowed-tools: Read, Grep, Glob
---
# TypeScript 規約
定義新型別前**務必**用 Grep 搜尋既有類似型別；非同步函式**務必**明示 Promise 型別。
🧪 含程式碼例能提升追從性研究顯示：提示中除抽象規則外，附上「類似程式碼例」，可讓 LLM 的成功率最多提升 3 倍。所以技能/指令裡多放具體範例。

鉤子 Hook：以程式「強制」規則

斜線指令與技能都依賴 LLM 推論、無法保證 100%。實務上有些規則必須絕對遵守（如「絕不可改 db.production.sql」）。鉤子在生命週期特定時機執行程式、決定論式運作，能 100% 確實。

共 10 種；PreToolUse 可阻擋（回傳結束碼 2 ＝禁止該操作並通知原因）：

鉤子時機可阻擋用途
PreToolUse工具執行前✓防止禁止操作、驗證
PostToolUse工具執行後—自動格式化、記日誌
Notification / Stop通知 / 回應結束—桌面通知
PreCompact / SessionStart / SessionEnd …各生命週期點—壓縮前保存、初始化、清理

7.3　強化與外部系統的連動

MCP 為 Claude Code「增加能做什麼」（新操作），如加 GitHub MCP 就能 create_pull_request；但「怎麼建 PR」的規則 MCP 不管——那是技能的事（定義格式/規則）。兩者互補：MCP 增加「能做什麼」，技能定義「怎麼用」。技能與 MCP 從 Claude 看都同列為「工具」。

指令式連動：用 Bash 操作 CLI

不是所有系統都有 MCP，也常要連組織內自有/舊系統。Bash 能執行任意 shell 指令：① 用既有 CLI（如 gh issue list --label "bug"）② 自製 CLI（把部署一連串步驟寫成腳本，一句「部署到 staging」全自動）。

觀點MCP指令式連動
認證協定層級（OAuth 等）依 CLI 工具
彈性受 MCP 功能限制指令可做的都能用
組織內系統需自製 MCP 伺服器既有腳本直接用

安全：Sandboxing 與 Dev Container

Bash 很強、但缺限制會洩漏機密或誤改系統檔。Sandboxing（沙箱化）以 OS 層級限制：① 檔案系統——只能寫目前目錄及子目錄，讀取則除機密檔（.env、~/.ssh、~/.aws…）外可讀；② 網路——只允許清單內網域，越界即擋並通知。它用 bubblewrap(Linux)/Seatbelt(macOS) 實作，連 prompt injection 也擋，所有子行程（npm/git/curl）都繼承邊界。用 /sandbox 啟用，settings.json 可細調（表 7.12）。

🚪 逃生艙與 Dev Container 有些指令（如 docker）沙箱內跑不了 → 逃生艙會分析失敗、提議「在沙箱外重試」（需你核准）。更強的隔離用 Dev Container（容器整體隔離、防火牆白名單網路）。--dangerously-skip-permissions 跳過所有確認、風險極高（可能讀 ~/.ssh、外洩、改系統檔），務必搭配 Dev Container 使用。

💡 COLUMN：MCP × 程式碼執行的效率化 接太多 MCP 會有兩個問題：① 所有工具定義事先載入情境（光 Playwright MCP 32 個工具就耗數千 token，多接幾個可達數十萬）② 中間結果全進情境（無障礙樹可達數萬 token）。Anthropic 的解法：把 MCP 工具包成 TypeScript 函式放檔案系統，代理只讀需要的函式並執行、內部呼叫 MCP——可漸進式揭露、在程式碼內先過濾再回給模型、用迴圈/條件組合多工具、保存結果重用。文章報告 token 用量削減 98.7%。代價是需額外的沙箱化與資源限制。
