把規格驅動開發的流程機制化（設計篇）

作者：西見公宏。結合前面所學，把第 4 章體驗的規格驅動開發「用 Claude Code 機制化」：以斜線指令定義流程、以技能定義專屬指示、以子代理執行獨立處理，目標是把從構想筆記到文件生成、功能開發都自動化。本章用第 8 章的範例儲存庫（已備好環境與提示設定），在 Dev Container 上運作。

🎯 本章三主角 斜線指令（流程）＋技能（做法）＋子代理（獨立驗證）。第 9 章再用無頭模式把它們自動跑起來。

8.2　機制化的基本設計

整體工作流程（四步）

① 建立構想筆記（docs/ideas/initial-requirements.md）→ ② /setup-project 生成 6 份永續性文件 → ③ /review-docs 用子代理審查並修正 → ④ /add-feature 進行功能開發（引導檔→實作→測試→驗證）。
人類只在「斜線指令內指示的核准點」介入；其餘由 Claude Code 執行、人類確認後放行。
圖 8.1　以斜線指令構成的工作流程

為什麼要「事先準備好開發環境」

🧱 SetupBench 論文（Microsoft Research, 2025/7） 93 個實任務測 AI 代理的環境建構能力：成功率最高的 Sonnet 4 僅 62.4%，且成功案例中 38–69% 步驟是無謂作業。失敗模式：① 漏裝測試工具（裝了 requirements.txt 卻沒裝 pytest）② 推測設定值出錯（亂猜連接埠）③ 臨時性設定（shell 重啟後 PATH 失效）。結論：環境建構對 AI 是高難度任務，長期專案宜由人類事先建好。

本章用 Dev Container 整備環境（自動裝 Node LTS＋Claude Code），並在 package.json 備好 lint/format/typecheck/test 指令。

{
  "scripts": {
    "build":"tsc","lint":"eslint .","format":"prettier --write .",
    "typecheck":"tsc --noEmit","test":"vitest run","test:coverage":"vitest run --coverage"
  }
}
⚠️ 關鍵提示叫它跑的指令（如 npm run lint）一定要能成功。若實際執行失敗，Claude Code 會陷入恐慌、動作不穩——提示與環境必須一致。

目錄結構也事先定好：docs/（永續性文件）、.steering/（作業單位文件）、.claude/（commands/skills/agents）、CLAUDE.md（全專案規則）。

8.3　以斜線指令自動化工作流程

把第 4 章對話流程原樣寫成提示。三個指令：

指令做什麼核心
/setup-project從構想筆記生成 6 份永續性文件只第一份要核准，其餘自動連生
/review-docs用 doc-reviewer 子代理審查文件獨立情境、不污染主代理
/add-feature從引導檔→實作→測試→驗證全自動實作迴圈＋例外規則

/setup-project：自動產生 6 份永續性文件

斜線指令以 Markdown 放在 .claude/commands/，檔名即指令名。它先讀 docs/ideas/ 所有筆記，再用對應技能逐份生成（prd-writing→functional-design→…），只在第一份 PRD 要求核准，核准後其餘 5 份自動連生（各份參照前一份、確保一致）。

> /setup-project
● 讀取構想筆記 docs/ideas/initial-requirements.md
● Skill('prd-writing') 生成 docs/product-requirements.md
「PRD 完成，請確認；核准後進入下一份。」
[使用者 OK] → 自動生成 functional-design / architecture / repository-structure / development-guidelines / glossary

/review-docs：用子代理審查

以「文件路徑」為引數，委派給 doc-reviewer 子代理，提示明確指定觀點：① 完整性 ② 具體性 ③ 一致性 ④ 可測量性（PRD）。子代理在獨立情境讀大量檔做審查，回傳報告給主代理摘要——不消耗主代理情境。

/add-feature：功能開發全自動

以「功能名」為引數。流程：① 建引導目錄與三空檔（requirements/design/tasklist）② 讀 CLAUDE.md 與 docs/ 理解專案 ③ 用 Grep 調查既有樣式 ④ 以 steering 技能（計畫模式）生成三份引導檔 ⑤ 實作迴圈 ⑥ implementation-validator 驗證＋跑 test/lint/typecheck ⑦ 更新文件。

實作迴圈（圖 8.19）：讀 tasklist.md → 有未完成任務？→ 執行最前面的未完成任務（steering 實作模式＋遵守 development-guidelines）→ Edit 把 [ ] 改 [x] → 回頭重複，直到全部 [x] 才停。
圖 8.19　以任務清單為基礎的實作迴圈
🧯 例外處理規則（圖 8.20） 迴圈中自律處理：規則A 任務太大→拆成更小子任務；規則B 有明確技術理由不需要→以 [x] ~~任務名~~ (理由) 更新。絕對禁止：無故跳過未完成任務、無理由放置就結束、向使用者徵詢判斷。並在提示註明「完全自動執行、各步驟完成立即進入下一步、勿中途徵詢」——這是為無頭模式而設計。

8.4　以技能載入特化指示

技能由 Claude 自動載入，也可在提示明確要求載入。要點是以適當粒度拆分。本章把技能分兩類：

類別技能用途
文件生成（成果物單位）prd-writing / functional-design / architecture-design / repository-structure / glossary-creation / development-guidelines各生成一份永續性文件
開發流程（任務狀況單位）steering / development-guidelines引導檔管理／程式碼規約
表 8.1　本章使用的技能一覽

prd-writing 把文件結構放 template.md，SKILL.md 指示「讀範本、把佔位符換成具體內容」。

✍️ 撰寫穩定提示三要點 ① 斷定式：用「務必含使用者故事」而非「可能的話請含」。② 定量式：「定義主要人物誌 1 人、次要 1–2 人」「KPI 設 2–3 個」。③ 給具體判斷基準：附「詳細度適中/不足/過剩」的範例，避免「請適切判斷」。

steering 技能用「模式」切換動作：模式1 計畫（從範本建三份引導檔）、模式2 實作（最重要：始終開著 tasklist.md、每完成一任務即時 Edit 打勾，禁止只用 TodoWrite、禁止跳過/留未完成）、模式3 驗證與回顧（確認全 [x]、記錄工夫/問題/設計變更理由/改善點）。development-guidelines 技能明示「既有 docs/development-guidelines.md 最優先」，並把細節拆到 guides/implementation.md、guides/process.md 按需參照，使 SKILL.md 精簡。

8.5　以子代理進行情境工程

把「需讀大量檔的審查/驗證」交給子代理，省主代理情境。

doc-reviewer：文件審查

從 5 觀點評估（完整性、明確性、一致性、可實作性、可測量性），明確定義檢查項目防疏漏，回傳「評價表＋良好點＋依〔必須〕/〔建議〕分級的問題（含箇所/理由/改善案）」。也可從 /review-docs 明確呼叫。

implementation-validator：實作品質驗證

從 5 觀點驗證：規格遵循、程式碼品質、測試覆蓋率、資安、效能。特徵是邊讀需求規格文件、邊比對實作，並執行 npm run lint、npm test --coverage、tsc --noEmit 取得定量指標，明確報告「實作與規格的相異點」（含影響與建議）。它在 /add-feature 最後驗證階段被啟動，使無頭執行時也能自律修正。

8.6　本章小結

✅ 一句話總結用斜線指令（流程）＋技能（做法）＋子代理（獨立驗證），把規格驅動開發從「人工對話」變成「可重複、可自動」的機制。

關鍵心法：事先備好環境與可執行的指令、提示要斷定/定量/給基準、自動執行要明確定義例外規則與「不中途停」。第 9 章將用無頭模式把這套機制實際自動跑起來。
