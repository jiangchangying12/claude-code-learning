向達人學習規格驅動開發

作者：吉田真吾。本章以故事形式，跟著新手「田中先生」與「達人」，體驗用 Claude Code 從構想到上線的開發。核心是規格驅動開發（Spec-Driven Development）——這是全書最關鍵的一章。

4.2　先憑感覺做做看（Vibe Coding 的坑）

田中先生憑感覺開發任務管理 App，依序踩到四個坑：

① 需求/規格缺漏：關掉再開，任務消失（沒持久化）。
② 規格落差傳達不了：想要「雙擊行內編輯」，卻做成「按鈕編輯」，來回多次還越改越亂。
③ 程式碼變脆弱：加優先度後改一處壞別處，最後整個畫面打不開。
④ 缺文件：同事想幫忙也看不懂「想做什麼、做到哪」，只能舉手投降。
圖 4.1 / 4.2　憑感覺（Vibe）做出來、又被改壞的 App
🧨 失敗根因不是工具不好，而是人與 AI 之間缺少「就 What（要做什麼）與 How（怎麼做）達成共識」的流程。

4.3　規格驅動開發的基礎

🎯 核心：共識的兩個軸 What（使用者課題、價值、成功定義、優先序）以產品需求規格書、機能設計書表達；How（技術、架構、品質、部署）以架構設計書、開發指南表達。文件是「記憶裝置」，達成共識才是本質。

兩類文件、兩種生命週期：

類型位置定位內容
永續性文件docs/整體 What/How，少更新，是「北極星」PRD、機能設計、架構、儲存庫結構、開發指南、詞彙表
引導檔.steering/[日期]-[標題]/「這次作業做什麼」requirements / design / tasklist（可加 blockers / decisions）
圖 4.3 / 4.4　What/How 兩軸與「永續性文件＋引導檔」由 CLAUDE.md 編排

由 CLAUDE.md 編排整個流程與規則：定義文件結構、作業順序、要「一次做一份、逐處確認核准」。並列出 Claude Code 在開發各環節的使用時機（構思、需求/機能設計、實作/測試、基礎設施、疑難排解、上手導覽）。

4.4　從構想到 MVP（4.4–4.8）

4.4 構思：把 Claude Code 當對打對象腦力激盪、收斂出 MVP（如「CLI 優先＋優先度自動推測」）。
4.5 製作 PRD：用技能生成產品需求規格書，再讓 Claude 自己審查自己的 PRD（附上檢查觀點），人類審查前先發現問題。
4.6 其餘永續性文件：機能設計、架構、儲存庫結構、開發指南、詞彙表，逐份生成、確認、核准。
4.7 引導檔：建 requirements/design/tasklist，把任務細化。
4.8 實作：依 tasklist 推進，跑品質檢查與測試，做出可動的 MVP。
圖 4.5–4.9　從構想筆記 → 文件 → 引導檔 → 實作出 MVP
🏆 五個教訓 ① 臨時湊合的實作會產生負債　② AI 是最佳對打（腦力激盪）對象　③ AI 也用於審查/測試/驗證　④ 文件是永遠指方向的北極星　⑤ 盡早展示能動的東西（重視 MVP）。
心法：AI 是提案者、人類是決定者——最終決策由人做。

4.9　回顧（Before / After）

Before（Vibe Coding）After（規格驅動＋CLAUDE.md）
實作憑靈感、無全貌以文件明確方向
程式碼混亂分層、可維護
測試無高覆蓋率實測
成果花 3 天做出不會動的東西1 天達成 MVP、2 週上線（預定）
最大差別＝流程的明確化：用 CLAUDE.md 編排流程與規則，作業就能毫不迷惘、安全推進

4.10　本章小結

✅ 三個重點 ① Vibe Coding 的極限：憑靈感會生技術債，需系統化做法。
② 以記憶（CLAUDE.md）編排開發工程：定義規則、一次做一份、細審變更。
③ 規格驅動開發：永續性文件定義整體並維持最新，引導檔管理每次作業。
